## Цель лабораторной работы

Реализовать ETL‑процесс, который:

- извлекает сырые данные из открытого источника (ReManga API),
- оркестрируется через Apache Airflow,
- загружает слой ODS в **3 разных хранилища**,
- содержит **минимум 3 DAG**,
- включает **сравнительный анализ** выбранных хранилищ.

## Источник данных

ReManga public API (top titles):

- `GET https://api.remanga.org/api/v2/titles/top/?count=20&page=1&period=new&section=new&tag=all`
- `GET https://api.remanga.org/api/v2/titles/top/?count=20&page=1&period=monthly&section=new&tag=all`
- `GET https://api.remanga.org/api/v2/titles/top/?count=20&page=1&period=year&section=new&tag=all`

Дополнительно, чтобы собирать данные “с разных разделов” и в объёме **не менее 100 элементов**,
ETL перебирает `section` из набора: `new`, `manga`, `manhwa`, `manhua`, `comics`
и делает пагинацию `page=1..5` при `count=20` (итого \(5 \times 20 = 100\) элементов на каждый `(period, section)`).

## Архитектура (Docker + Airflow)

Файл: `docker-compose.yaml`

Важно: при запуске `docker compose` рабочая директория должна быть `MangaReview/` (или нужно установить `AIRFLOW_PROJ_DIR`), чтобы корректно примонтировались каталоги `dags/`, `logs/`, `config/`.

- **Airflow (CeleryExecutor)**: webserver / scheduler / worker / triggerer / init.
- **Redis**: брокер Celery.
- **PostgreSQL (airflow)**: метаданные Airflow.

### ODS-хранилища (3 сервиса)

1) **PostgreSQL ODS** (`postgres_ods`, БД `ods_manga`)

- Хранит “лёгкую” нормализацию (period, rank, title_id, title_name, rating) + `raw JSONB`.
- Удобен для OLAP‑похожих запросов и дальнейшего DDS/DM.

2) **MongoDB ODS** (`mongo_ods`, БД `ods_manga`)

- Документоориентированное хранение сырых JSON.
- Позволяет хранить структуру “как есть”, без миграций схемы.

3) **MinIO (S3) ODS** (`minio`, bucket `ods-remanga`)

- Хранение сырых JSON‑файлов (data lake подход).
- Удобно для истории выгрузок, бэкапов и последующей пакетной обработки.

## Реализация ETL (DAG)

Общий модуль: `dags/remanga_ods_utils.py`

- **Extract**: запросы к ReManga API по периодам `new/monthly/year`, разделам `section` и пагинации (`extract_top_titles`).
- **Transform**: минимальная нормализация + `raw` (`transform_to_rows`).
- **Load**:
  - Postgres: `load_rows_to_postgres` (upsert по `(period, item_key)`).
  - Mongo: `load_rows_to_mongo` (upsert по `_id = period:item_key`).
  - MinIO: `upload_extracted_to_minio` (raw JSON по `section/period/page` и времени выгрузки).

### DAG 1: PostgreSQL ODS

Файл: `dags/remanga_ods_to_postgres.py`  
DAG id: `remanga_top_titles_to_postgres_ods`

Цепочка: `extract_remanga_top -> transform_to_rows -> load_to_postgres`

### DAG 2: MongoDB ODS

Файл: `dags/remanga_ods_to_mongo.py`  
DAG id: `remanga_top_titles_to_mongo_ods`

Цепочка: `extract_remanga_top -> transform_to_rows -> load_to_mongo`

### DAG 3: MinIO/S3 ODS

Файл: `dags/remanga_ods_to_minio.py`  
DAG id: `remanga_top_titles_to_minio_ods`

Цепочка: `extract_remanga_top -> upload_to_minio`

## Сравнительный анализ хранилищ

| Критерий | PostgreSQL (JSONB + поля) | MongoDB (documents) | MinIO/S3 (files) |
|---|---|---|---|
| Схема/эволюция данных | Требует продуманной схемы, но можно хранить `raw JSONB` | Максимальная гибкость (схема не обязательна) | Схема “в файле”, эволюция простая, но без индексации |
| Аналитические запросы | Сильные SQL/агрегации, удобно для витрин | Возможны агрегации, но сложнее для OLAP | Нужен внешний движок (Spark/Trino/Presto/ClickHouse и т.п.) |
| Хранение сырых ответов API | Хорошо (JSONB) | Отлично (нативные документы) | Отлично (исторические снепшоты файлов) |
| Идемпотентность загрузки | Upsert по ключам | Upsert по `_id` | Ключи объектов по времени выгрузки (история) |
| Рекомендация для дальнейших ЛР | База для DDS/DM | Хорошо как “сырое” хранилище | Хорошо как data lake/архив |

**Итоговый выбор для аналитики**: PostgreSQL, так как даёт удобный SQL и при этом сохраняет `raw` в JSONB. MongoDB и MinIO полезны как альтернативные/дополнительные ODS (гибкость схемы и история выгрузок).
